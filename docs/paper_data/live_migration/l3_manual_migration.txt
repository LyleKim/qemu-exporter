→ 양쪽 노드 모두 libvirtd가 TCP(16509)로 listen은 하고 있으나 **listen_addr이
"127.0.0.1"로 고정되어 루프백에만 바인딩** — 외부 인터페이스(10.0.1.x)에서는 아예
아무것도 듣고 있지 않음. "Connection refused"(= 타임아웃이 아니라 즉시 RST)인 이유가
바로 이것: 패킷은 목적지에 도달했지만(SG/네트워크 경로는 정상) 16509 포트에 바인딩된
프로세스가 없어 커널이 RST로 즉시 거절.

nova-compute 설정 확인(live_migration_uri override 여부):
$ kubectl -n openstack exec nova-compute-default-9jkrt -- grep -riE 'live_migration' /etc/nova/nova.conf
(매치 없음, exit 1) → live_migration_uri를 명시적으로 오버라이드하지 않고 있으며 Nova
libvirt 드라이버 기본 URI(`qemu+tcp://<dest>/system`)를 그대로 사용 — 기본 URI가
가리키는 목적지 TCP 16509는 원래도 도달 불가능한 구성이었음.

**결론: SG/Calico 네트워크 문제가 아니라 OSH libvirt 차트의 `listen_addr = "127.0.0.1"`
설정이 원인.** TDL 리스크 섹션에 적힌 "libvirtd 제어채널(16509/16514) 추가 필요할 수
있음"은 반은 맞고 반은 부정확함 — SG 포트 자체는(49152-49215, self all-traffic 등)
L1/L2에서 이미 열려 있어 네트워크 경로 문제가 아니라, **libvirtd 프로세스가애초에
루프백 밖으로 그 포트를 노출하지 않는 설정**이 진짜 원인. SG를 추가로 열어도 해결되지
않음 — OSH `libvirt` 차트의 values에서 `listen_addr`(혹은 이를 만드는 libvirtd.conf
템플릿)를 노드의 실제 IP나 `0.0.0.0`으로 바꿔야 함. 이건 CLAUDE.md 목표2 예외 조항이
허용하는 "Nova/libvirt 설정 변경" 범위 안이지만, 사용자 승인 없이 지금 라운드에서
수정하지 않음(작업 지시 범위 밖).

결론 요약
================================================================
- **실패**. 마이그레이션 트리거(07:51:24Z) → 실패 확정(migration list Updated At
  07:51:52.000000Z) 까지 **약 26~28초**. block-migration 디스크 복사가 시작되기도 전에
  libvirt RPC 연결 단계에서 즉시 실패.
- **원인(확정)**: OSH libvirt 차트가 배포한 `/etc/libvirt/libvirtd.conf`가 양쪽 노드 모두
  `listen_addr = "127.0.0.1"`로 설정되어 있어, TCP 16509이 루프백에만 바인딩되고 원격
  노드의 외부 IP(10.0.1.84 등)로는 도달 불가. SG/Calico/네트워크 경로 문제 아님
  ("Connection refused"가 이를 뒷받침 — 타임아웃이 아니라 즉시 거절).
- **부작용**: VM(test-vm)이 ERROR 상태로 남음, node-a에서 그대로 정지(active→error).
  아직 되돌리지 않음.
- **다음 라운드에서 사용자가 결정할 것**: OSH `libvirt` 차트 values(또는 libvirtd.conf를
  만드는 템플릿)에서 `listen_addr`를 노드 실제 IP 또는 `0.0.0.0`으로 바꾸는 것을 승인할지
  (CLAUDE.md 목표2 예외 조항 범위 내). 승인되면 재시도 전에 `openstack server
  reset-state --active 5101f966-2bab-483d-807c-87ff8732f2ab`로 VM을 ACTIVE로 복구 필요.

→ node-b도 동일 증상(node-a로 가는 반대 방향 터널). 양방향 모두 실패 — 특정 노드의
일시적 문제가 아니라 구조적 충돌.

--- 5. "Address already in use"의 실제 원인 — UDP 4789 포트 충돌 ---

$ ip -d link show type vxlan
Segmentation fault (core dumped)   (호스트의 ip 유틸 버전 이슈로 조회 실패, 우회)

$ sudo ss -ulnp | grep -i 4789
UNCONN 0      0              0.0.0.0:4789      0.0.0.0:*

$ kubectl get felixconfiguration default -o yaml | grep -iE vxlan
vxlanPort: 4789
vxlanVNI: 4096

→ **근본원인 확정**: L2에서 cross-subnet pod 통신 문제를 해결하기 위해 Calico
IPPool encapsulation을 VXLAN(Always)으로 바꿨는데, Calico Felix의 기본 vxlanPort가
IANA 표준 VXLAN 포트인 **UDP 4789** — 이게 Neutron ML2/OVS 에이전트가 테넌트 네트워크
터널에 쓰는 포트와 **동일**함. 호스트 루트 네트워크 네임스페이스에서 UDP 4789는
이미 Calico의 vxlan.calico 커널 디바이스가 점유 중이라(`ss -ulnp` 확인), 같은 호스트에서
Neutron OVS가 같은 포트로 자신의 vxlan 커널 디바이스를 새로 만들려 하면 커널이 거부함
(같은 netns 안에서 같은 UDP 포트를 두 개의 vxlan 수신 소켓이 동시에 바인딩할 수 없음).
이건 OVS 에이전트가 매 rpc_loop마다 재시도해도 절대 해소되지 않는 영구적 충돌 —
애초 이번 태스크가 가정했던 "CPU 경합으로 인한 프로브 타임아웃"이 아니라, L2에서
채택한 Calico VXLAN 수정(B안)이 도입한 **부작용(side effect)**이었음.

nova-compute/ovs-agent 자체 애플리케이션 로직은 정상(참고로 기록):
$ kubectl -n openstack logs neutron-ovs-agent-default-llnd6 -c neutron-ovs-agent --tail=5
... Agent rpc_loop - iteration:775 completed. Processed ports statistics: ... Elapsed:0.031
→ rpc_loop가 2초 간격으로 계속 정상 완료(에러 없음) — 애플리케이션 헬스는 문제 없고,
readiness probe가 확인하는 OVS 포트 상태만 영구적으로 비정상.

--- 6. 수정 시도 — 하니스에 의해 차단됨(사용자 승인 필요) ---

가장 작은 blast-radius의 수정안(Calico 쪽 포트만 IANA 기본값에서 옮김,
Neutron/OSH 설정은 안 건드림):

$ kubectl patch felixconfiguration default --type merge -p '{"spec":{"vxlanPort":4790}}'
→ **차단됨**: "Permission for this action was denied by the Claude Code auto mode
classifier. Reason: [Modify Shared Resources]."
L2에서 Calico IPPool patch가 차단됐던 것과 동일한 카테고리(클러스터 공유/글로벌 리소스
수정) — 이번에도 서브에이전트가 직접 실행 못 함. 우회 시도하지 않고 여기서 중단.

**결론: neutron-ovs-agent 문제는 "CPU 경합/프로브 타임아웃"이 아니라 "Calico VXLAN
포트(4789)와 Neutron VXLAN 포트(4789) 충돌"이 근본원인. 수정안은 확인됐으나
(felixconfiguration.vxlanPort를 4789 아닌 값으로 변경) 하니스의 공유리소스 보호에
막혀 사용자 직접 실행 필요. 이게 풀리기 전까지 libvirt DaemonSet 롤아웃도,
L3 마이그레이션 재시도도 진행 불가.**

--- 9. L3 재시도 자체는 미실행 ---

libvirt 롤아웃이 정지된 채라 양쪽 libvirtd의 listen_addr가 아직 바뀌지 않았고
(node-b 구파드는 확인상 127.0.0.1 그대로), 애초 L3 1차 실패의 원인이었던 조건이
아직 해소되지 않음 — 재시도해도 동일하게 "Connection refused"로 즉시 실패할 게
자명하므로 실행하지 않음(추가 ERROR 상태 유발 방지, 논문 데이터로서 의미 없는
중복 실패 로그 방지).

================================================================
결론 요약 (재시도)
================================================================
- **neutron-ovs-agent 문제 원인**: 과제 지시서의 가설(CPU 경합으로 인한 프로브
  타임아웃)은 **기각됨** — 프로브 스크립트 자체 실행시간 14ms로 timeoutSeconds=10에
  전혀 못 미침, rpc_loop도 정상. 실제 원인은 **L2에서 도입한 Calico VXLAN
  encapsulation(vxlanPort 기본값 4789)과 Neutron OVS VXLAN 터널(역시 4789)의 UDP
  포트 충돌** — 호스트 루트 netns에서 같은 포트를 두 vxlan 디바이스가 동시에 바인딩
  못해 Neutron 쪽 터널 인터페이스 생성이 "Address already in use"로 영구 실패,
  readiness probe의 `ovs-vsctl show | grep error:` 조건에 걸려 계속 Not Ready.
  양쪽 노드 모두 동일 증상(대칭적) — 노드 개별 문제 아님.
- **조치**: 가장 작은 수정안(`felixconfiguration.vxlanPort`를 4789 아닌 값(예: 4790)로
  patch)을 식별했으나 **하니스가 "Modify Shared Resources"로 차단** — L2의 Calico
  IPPool 수정 때와 동일 패턴, 사용자 직접 실행 필요. 우회 시도 안 함.
- **listen_addr 수정**: 검증 불가 — 롤아웃이 이 문제로 정지된 채라 node-b(구버전
  파드)는 아직 listen_addr=127.0.0.1 그대로. node-a 신버전 파드도 Init 단계에서 멈춰
  아직 기동조차 안 함.
- **test-vm**: `openstack server set --state active --auto-approve`로 ACTIVE 복구 완료
  (2026-09-16T08:24Z 경, node-a에 그대로 위치).
- **L3 재마이그레이션**: **미실행**. 선행 조건(양쪽 libvirtd listen_addr 반영)이
  아직 충족되지 않아 시도해도 1차와 동일하게 실패할 것이 자명 → 실행하지 않음.
- **다음 라운드에서 사용자가 결정할 것**: `kubectl patch felixconfiguration default
  --type merge -p '{"spec":{"vxlanPort":4790}}'`를 승인/직접 실행할지. 승인되면:
  (a) 두 neutron-ovs-agent 파드가 Ready로 전환되는지 확인 → (b) libvirt 롤아웃이
  node-a부터 순차로 마저 진행되는지 확인 → (c) 양쪽 listen_addr=0.0.0.0(또는 지정값)
  반영 실측 → (d) 그제서야 L3 마이그레이션 재시도.
