## SUMMARY -- 3 measured metrics (v2, 2026-09-19 node clock; evaluation_interval=15s tuning applied)

Pre-flight confirmed: `global.evaluation_interval: 15s` live in running Prometheus config
(`/api/v1/status/config`), rule group `qemu-contention` interval=15 (was 60 in v1),
threshold unchanged at 0.005, cpu-hog replicas=4 (same dosage as v1, sufficient to cross
threshold, did not need to scale to 8), zero OSH pod instability throughout (26/26 mid-scenario
polls + final check all show NONRUNNING_PODS=0 / no CrashLoopBackOff or Evicted pods).

1. 임계치초과 -> alert 발생 지연:
   - Rule mechanism confirmed fixed: rule group eval interval is now 15s (was 60s in v1), and
     `for: 30s` now resolves to exactly 2 evaluation cycles as designed, deterministically:
     pending activeAt=2026-09-19T17:12:10.729949095Z -> firing at activeAt+30s =
     **2026-09-19T17:12:40.729Z** (Prometheus's own for-duration arithmetic, not an estimate).
   - IMPORTANT CAVEAT (found this run, not present in v1): the PSI(some) rate hovered right at
     the 0.005 threshold under replicas=4 load (crossing points found: 0.0043->0.0053 range,
     with a dip back to ~0.0049 for ~15s around 17:11:50-17:12:05Z) -- this caused the FIRST
     pending instance (activeAt=17:11:25.729Z) to be reset before it could reach `for: 30s`,
     because the condition briefly evaluated false at the 17:11:55.729Z evaluation. A second,
     uninterrupted pending then started at 17:12:10.729Z and successfully fired 30s later. This
     flicker is a property of this exact load level sitting close to the threshold, not a defect
     in the evaluation_interval fix -- v1's run happened to have a cleaner, sustained crossing at
     this same replica count.
   - Two honest delay figures, both reported (methodology differs only in which crossing is used
     as the reference point -- pick per what the paper needs):
     (i) STRICT, same method as v1 ("first sample >= threshold via 5s-step range query"):
         first crossing = 2026-09-19T17:11:25Z (value 0.005279) -> firing 17:12:40.729Z
         => **지연 = 75.7s** (vs v1's 100.7s -- 24.8% reduction)
     (ii) From the crossing that actually initiated the successful (non-reset) pending:
         2026-09-19T17:12:05Z (value crossed back above 0.005) -> firing 17:12:40.729Z
         => **지연 = 35.7s** (vs v1's 100.7s -- 64.5% reduction; this number isolates the fix's
         effect cleanly, since it's ~for:30s + <1 eval-cycle alignment slack, exactly the expected
         behavior once evaluation_interval=15s)
   - **Conclusion**: the evaluation_interval fix worked exactly as diagnosed -- the alerting
     pipeline is no longer bottlenecked by a 60s default eval loop. The 75.7s "worst case" number
     is inflated by an unrelated threshold-flicker artifact from running the load at the same
     replicas=4 dosage as v1; a slightly higher/steadier load (e.g. replicas=5-6, untested this
     session, out of scope for this re-measurement) would likely collapse both numbers toward the
     ~36s figure by avoiding the flicker.
