--- 3. 버그 발견: qemu-exporter 스크레이프가 2노드에서 한쪽만 잡힘 ---

최초 확인 시 exporter counter는 정상 증가(node-b 파드에서 1.478865 -> 1.514044,
15초간)하는데 Prometheus의 openstack_vm_cpu_pressure_stall_seconds_total 인스턴트 쿼리는
빈 결과. 원인: 기존 scrape_config가 ClusterIP Service(qemu-exporter.openstack.svc.cluster.
local:9179)를 static target으로 잡고 있었음 — DaemonSet은 노드당 1개 파드인데 Service
뒤에 2개 엔드포인트가 있으면 kube-proxy의 connection stickiness 때문에 Prometheus는
매번 같은 파드 하나만 계속 스크레이프(이번 경우 node-a 파드, VM이 없어 0으로 유지).
단일노드 때는 문제가 될 수 없었던 설계 — 2노드에서 처음 드러난 버그.

수정: kubernetes_sd_configs(role: pod, namespace: openstack, label app=qemu-exporter)로
전환해 각 파드 IP를 직접 타겟팅하도록 prometheus.yaml 변경(cAdvisor job과 동일 패턴).
ConfigMap만 바꾸고 Deployment 스펙은 안 바뀌어 자동 재시작이 안 걸려서
`kubectl -n monitoring rollout restart deploy/prometheus`로 수동 재기동 필요했음.

수정 후 확인:
$ curl .../api/v1/targets?state=active | ...
  qemu-exporter http://192.168.86.255:9179/metrics up   (node-a, VM 없음)
  qemu-exporter http://192.168.235.131:9179/metrics up  (node-b, test-vm 있음)
$ curl .../api/v1/query?query=openstack_vm_cpu_pressure_stall_seconds_total
  1개 series 반환(node-b 파드분), instance_uuid=1bfa7dda... 정상.

--- 4. cpu-hog로 부하 유발, threshold 문제 발견 ---

$ kubectl apply -f cpu-hog.yaml
$ kubectl -n default patch deployment cpu-hog --type merge \
    -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/hostname":"ip-10-0-1-207"}}}}}'
  (test-vm이 있는 node-b를 직접 지정 — cpu-hog.yaml 자체엔 nodeSelector 없음)

replicas=4로 시작, 5분 이상 관찰해도 rate(...[1m]) 0.005~0.012 사이에서만 등락,
TDL 원안의 threshold 0.5에는 전혀 근접 못함. replicas=8로 증량(node-b는 8vCPU,
load average는 4.46/8까지만 올랐다가 8개로도 크게 안 오름 — TCG 소프트웨어 에뮬레이션 +
컴퓨트 전용 노드라 절대적인 경합 강도 자체가 목표1 논문 실측(Fig.3 피크 0.1467)과
비슷한 자릿수에 머무름).

**threshold 0.5는 TDL 문서에 처음부터 "Fig.3 실측(0.0117→0.1467)보다 훨씬 높게 잡은
잠정치, L6 재측정 후 보정 예정"이라고 명시돼 있었음** — 이번 실측으로 그 잠정치가
이 부하 패턴에서는 사실상 도달 불가능한 값임을 재확인. 사용자 확인 후 L4 게이트
통과 목적으로만 threshold를 임시로 낮춤(0.5→0.01→0.005, 관측된 rate 변동폭 상단이
0.005를 안정적으로 넘도록). deploy/monitoring/alert-rules.yaml에 ponytail 주석으로
"L6 재측정 후 실제 값으로 재조정 필요"를 명시해둠 — 이 0.005는 실사용 값이 아니라
파이프라인 검증용.

--- 5. Alert 발화 확인 ---

               "node":"ip-10-0-1-207","severity":"warning", ...},
    "annotations": {"instance_uuid":"1bfa7dda-638f-42a4-b377-287144591b6a","node":"ip-10-0-1-207"},
    "status": {"state":"active", ...},

**결과: Alertmanager API에 alert가 state=active로 정확한 instance_uuid/node 라벨과 함께
나타남 — L4 게이트 통과.** rule evaluate(pending, 06:58:06 근방) → firing(06:58:54)까지
약 30~40초, "for: 30s" 설정과 부합.
